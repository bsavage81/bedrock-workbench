# Workbench schema direction

## Item authoring (0.15.0)

tools/item-schema.cjs independently defines 52 built-in/legacy item components and emits schemas/item.schema.json through the common generator. It replaces the item entry point in the compatible official-schema cache (build 13), while generated component metadata omits our owned item names to avoid competing shapes and duplicate hovers. Existing foundational default-BP associations continue using the same item schema file. Every authored component and nested description links to its Microsoft Learn stable page.

Coverage includes consumables, equipment, tools, durability/sensors, mining, block/entity placers, projectile/shooter/throwable behavior, storage/bundles, kinetic/piercing weapons, icons, timing, sounds, tags, and documented historical forms. Required/numeric/enum checks are conservative; arbitrary fields and custom component values remain open. Known scalar/object wrappers, repair tag descriptors, numeric/string/versioned Molang amounts, single-string legacy seed targets, and historical vanilla identifier casing are retained. Deprecated component names/fields remain accepted while hidden from new-key suggestions. Format/experiment prerequisites and inter-component requirements are documented where established; exhaustive conditional enforcement and runtime behavior checks remain outside this pass. Microsoft Learn currently disagrees between start_using's if_first choice table and on_attack prose; both parse, only the documented choice-table spellings are suggested. Built-in durability sensor particle types are distinct from RP particle definition IDs.

Typed reference fields route to project and compatible vanilla blocks/items/entities/texture aliases/sound definitions. Molang tag predicates are not mistaken for names. Item tag declarations suggest existing project tags but allow new tags without unresolved-reference warnings. Vanilla item references are extracted using the same field contexts as diagnostics, capturing legacy aliases and engine sound events without adding duplicate canonical completion entries. Samples intelligence version 5/local index version 3 refresh older caches. The optional audit tool defaults to the v1.26.50.4 snapshot: node tools/audit-item-examples.cjs <samples.zip> <local-items-folder>.

Custom item components use the existing original JS/TS registration/parameter analyzer: item and block registries stay separate; saved IDs refresh; callback/parameter hovers and definitions navigate to sources; legacy ID arrays, nested fields and scalar examples work. Hints are advisory, not inferred validation contracts. Parameterless/unrecognized custom objects offer no guessed fields. Unsaved script buffers, general function-argument flow, external package types, exhaustive script reachability, and proving that registration executes remain limitations shared with blocks.

Verification: 79 Mojang v1.26.50.4 items and 64 SavageCraft items pass structural checks; all supported typed references in those 79 vanilla examples resolve using the matching samples. Saved-project validation of 721 JSON files reports zero errors/warnings, zero active information findings, and ten findings suppressed by existing user-authored rules. Native VS Code checks cover nested schema fields/validation, Learn links with one hover source, entry snippets, correct block/item list separation, custom item keys/legacy arrays/nested parameters/booleans/hovers/F12, saved registration refresh, project tags, and navigation during atomic project refresh.

## Original routes in 0.9.0

`recipe.schema.json` covers shaped, shapeless, furnace, brewing mix/container, smithing transform, and smithing trim. It checks nested ingredient/result types, counts, shaped pattern/key structure, and essential variant fields. It accepts string/object ingredients, item tags, object/array results, object/array unlock conditions, older two-part format versions, and legacy transforms without templates. Unknown recipe kinds remain structurally open; material reduction and engine-specific availability are not yet audited. Pattern-to-key consistency is a future semantic check.

Recipe tag strings suggest built-in stations appropriate to the recipe kind. An open string alternative preserves custom station tags. Internal `deprecated` tags found in vanilla samples are not suggested as crafting stations.

`texture-atlas.schema.json` covers RP item and terrain atlases, including string paths, arrays, and path objects with tint/overlay settings. Optional pack/atlas labels stay optional for existing add-ons. It does not verify that an image exists.

`sound-definitions.schema.json` covers the `sound_definitions` map, string/object audio entries, typed playback settings, nullable distances, and legacy flag strings. Category values stay open. Legacy flat root layouts and server sound definitions are outside this first audited scope.

These replacements currently use the existing schema runtime for engine targets 1.26.50 and newer; individual documents retain their older format versions. Other routes still use the official Mojang package. Unknown extension fields remain allowed. This is structural validation, not proof that a recipe/sound works in-game.

Definitions are maintained in `tools/generate-owned-schemas.cjs`; run `npm run schemas:generate` to recreate the checked-in JSON files. The generator reads no third-party schema files. Regression cases are maintained separately in `test/authored-schemas.test.cjs`.

## Block schemas and script registrations (0.10.0)

The original block schema is maintained in tools/block-schema.cjs and emitted to schemas/block.schema.json by the common generator. It replaces the official block entry point and the previous foundational block schema. This first batch covers the document wrapper, identifier, menu category, states, placement traits, permutations, and 23 common component definitions. Remaining built-in component names/fields can still receive compatible Mojang documentation assistance; overlapping authored rules are omitted from that generated reference to preserve our types and one hover source.

Audited shapes include friction/light values, mining/explosion unions, box vectors, geometry, materials, transformations, color representations, tick intervals, placement filters, loot, tags, and liquid interaction settings. Legacy forms and unknown fields remain open. Engine/format-specific feature availability, geometry/material pairing across permutations, state-expression evaluation, and the remaining built-in component payloads are future work. Material ambient-occlusion booleans remain accepted for older document versions.

Custom block and item registries are analyzed separately using the pinned Node-compatible @babel/parser package (MIT, shipped with its dependency notices). src/script-components.cjs is original Workbench analysis code. It never executes imports, handlers, constructors, or project statements. Discovery supports string literals, constant concatenation/templates/object members, lexical registry aliases, and relative named/default/namespace imports and reexports. Saved JS/TS source changes, renamed/deleted scripts, and imported-constant changes rebuild the registry view. Only behavior-pack source files up to 2 MiB each are inspected; type declaration files and ignored directories are excluded.

Registered component IDs are suggested at component keys, permutation keys, and legacy custom-component lists, with source/callback hovers and registration navigation. Custom JSON parameter values remain unrestricted. Components registered for the opposite pack-content kind receive an informational finding; unresolved/external IDs remain allowed. Runtime-computed IDs, general helper-call argument flow, third-party package exports, unsaved source buffers, and proof that registration code is reachable/executed are outside this initial scope.

In 0.11.0, custom parameter assistance combines callback second-argument `params` reads, literal-ID `getComponent(...).customComponentParameters.params` reads, supported TypeScript annotations/assertions, and saved block/item configurations. Nested keys, inferred types, scalar examples, boolean choices, and source navigation are advisory only. Unknown fields remain valid; this is not a runtime parameter contract. Local and direct relative imported types are supported; arbitrary function argument flow and external package type resolution are not. Existing project examples can contribute suggestions even when scripts are unavailable.

Geometry and texture suggestions are resolved by field context in src/content.cjs. Block geometries include pack IDs and vanilla full_block/cross; full_block_v1 requires both document format and target >= 1.26.0. Terrain/item atlas aliases come from project atlases and the compatible cached Mojang release; project aliases take precedence. Raw image-path fields remain separate. The reference cache intelligence version is 2 to refresh older atlas-free indexes. Go to Definition targets atlas keys and geometry identifiers.

## Document format compatibility

`src/format-versions.cjs` is shared by live diagnostics, Validate Pack, native schema generation, metadata completion and script component completion. `format_version` chooses a document dialect; it is independent of the project release version and is never bumped automatically. Numeric manifest schema versions are handled separately. Declared dotted document versions newer than the target engine produce warnings across indexed JSON files. Two-part legacy strings remain accepted.

`src/format-requirements.json` stores explicit minimum-version facts and source URLs from Microsoft's component documentation, not inferred introduction dates from the first sample found. `npm run docs:formats` explicitly refreshes facts from Microsoft's documentation source archive. The extractor distinguishes introduction notes from field property tables/subheadings, skips aggregate/versioned component index pages, and records material instance wildcard paths. Source parser tests prevent a field note from becoming a false whole-component minimum. These facts describe the documented component forms; experimental and historical behavior is not exhaustively documented. Unknown rules stay open.

BP block/item/entity components and documented fields are conditional on the file's format, including block permutations and entity component groups. Outdated components produce a shared `bedrock.formatVersion` warning; their incompatible current payload constraints are not applied to older dialects. Known field minima are advisory warnings and control suggestions. Direct custom block/item keys require format 1.21.90; the legacy `minecraft:custom_components` array remains readable and gets a deprecation warning in newer formats. Flower-pottable placement is restricted to root components from 1.26.20. This does not execute scripts or prove every engine/experiment combination.

The bundled unversioned item/block/entity static associations have been removed: project-scoped version-aware associations supply these schemas for arbitrary pack locations. Older engine targets receive owned schemas; the newer broad Mojang fallback routes are excluded. Cache build 15 includes the target in its identity. Compatible samples intelligence version 6 records observed document formats by pack side and folder, while saved project formats and documented component boundaries supplement suggestions. Geometry, particle, recipe and texture formats are not blindly replaced with the target engine string. Sample format observations are examples, not a closed list of all valid historical formats.

Outstanding audits: full historical removal/version replacement tables, every remaining nested shape transition, all experimental exceptions and every RP/other BP format dialect. Do not describe the current rules as complete historical engine validation. No source pack versions are rewritten by these checks.
