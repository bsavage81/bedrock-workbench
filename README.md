# Bedrock Workbench

A Windows-first VS Code extension for Minecraft Bedrock add-ons. The initial package targets Windows x64. Build into Minecraft's development folders and export stable releases with separate identities and branding.

## Command and vanilla assistance

Block JSON now uses our original document and common-component schemas. Script-registered custom block/item IDs appear in component keys, permutations, and legacy `minecraft:custom_components` arrays, with source hovers and Go to Definition. JS/TS analysis supports literal IDs, constant strings/templates, registry aliases, and relative imported/reexported constants; it refreshes after saved script changes. Scripts are parsed without execution. Custom parameter completions and hovers use saved script reads, supported TypeScript types, and existing block/item definitions, including nested names and example values. Go to Definition opens the relevant script or example. These are advisory hints; unknown parameters remain allowed. Runtime-computed IDs, general helper-call argument flow, and external package types are not resolved. Discovery scans behavior-pack source files up to 2 MiB each and does not prove that a registration runs in-game.

Creating an empty `[]`, `{}`, or `""` in a pack JSON/JSONC editor automatically opens available suggestions, including a new object after an existing function/condition. This uses the current schema and project completions, waits for the caret to settle, and stays quiet when no choices are available. It respects **Editor: Suggest On Trigger Characters**; Ctrl+Space remains available manually.

Supported JSON reference values include vanilla identifiers from the newest compatible released Mojang sample snapshot, alongside your project identifiers. `.mcfunction` files offer command names, metadata-backed argument choices, signature help, selector type/tag values, and nested `execute … run` completion. Function paths, literal scoreboard objective declarations, and selector tag additions are indexed from project function files. Project sounds and particles are also indexed. Snapshots are cached for offline use; Preview currently uses compatible released references and may omit Preview-only content.

This is completion assistance rather than a full command validator. Runtime-generated identifiers and script-registered custom commands are not yet discovered. Independently authored Workbench schemas validate block/item/entity components, client entities, loot tables, seven recipe variants, item/terrain texture atlases, and client sound definitions. They provide field completion, descriptions, and nested structural checks while retaining legacy forms and unknown extensions. Owned routes also support older project targets; the broader bundled official Mojang fallback catalog is enabled for targets 1.26.50 and newer. Blockception code and schemas are not included.

## Start

For a shareable test build, give testers the Windows `.vsix` release file or the tester ZIP containing that file and [installation instructions](TESTING.md). Installing from VSIX does not require access to the source repository.

1. Install the local `.vsix` using VS Code's **Extensions: Install from VSIX** command.
2. Run **Bedrock: Create New Project** to create a new add-on, or open an existing project containing `bedrock-project.json`. For an existing standard add-on with `BP` and `RP`, run **Bedrock: Initialize Existing Project** once.
3. Open the Bedrock activity-bar sidebar. Choose **Build beta** to compile without deploying.
4. Choose the Minecraft **release** or **preview** target. Use **Minecraft folder** to override discovery with that installation's `com.mojang` folder.
5. Choose **Deploy beta** for a manual deployment, or turn **Auto deploy** on. Saved changes and external changes, including added or deleted files, trigger deployment after a short delay. The project must be trusted.
6. Use **Deploy stable** to compile directly into the selected Minecraft installation's `behavior_packs` and `resource_packs` folders. Use **Export stable .mcaddon** for distribution instead.
7. Manual **Deploy beta**, **Deploy stable**, and **Export stable .mcaddon** commands ask for a version, prefilled with the project's current version. Canceling changes nothing. After a successful action, that version is written to the project and both source manifests, including module versions and dependencies linking BP/RP. Script API versions and UUIDs stay unchanged.

Use VS Code's standard Explorer to browse and edit project files. The Bedrock sidebar keeps the project name and build status at the top, followed by collapsible **Settings**, **Pack icons**, **Beta development**, **Stable releases**, and **Project tools** sections. Beta and stable tasks start expanded; the other sections start collapsed. VS Code retains your expansion choices as the sidebar refreshes. Select the project name at the top to open its settings.

Choose **BP pack icon** and **RP pack icon** in the sidebar to select PNG images from any local folder. Each selection is validated and copied into the appropriate source pack as `pack_icon.png`. The sidebar shows thumbnails, and the project name uses the BP icon with RP as a fallback. Thumbnails refresh when image contents change, even at the same filename. Canceling keeps the existing icon; an invalid image cannot overwrite it. With Auto deploy enabled, changing the source icon triggers the normal beta build.

## Create a new project

**Bedrock: Create New Project** asks for a name, parent folder, Minecraft Release or Preview target, engine version, PNG icon, JavaScript/TypeScript or no scripting, stable or beta Script APIs, and world experiment requirements. The same icon starts both packs; each can be changed later from the sidebar. The wizard checks current engine/API versions and experiment availability, with explicit version entry and bundled experiment choices when offline.

Review the final settings before creating anything. The wizard creates a new subfolder under the selected parent and refuses to replace an existing folder. Canceling before creation leaves the parent unchanged. It generates standard BP/RP content folders, linked format-2 manifests, pack icons, starter language files, project settings, a README and ignore rules. Scripted projects additionally receive a starter script, package.json and TypeScript/JavaScript editor settings. TypeScript compiles to the manifest's JavaScript entry point. Matching API typings can be installed during creation or later with **Bedrock: Install Script API Typings**.

New projects start at 1.0.0 with independent beta/stable identities. Auto deployment starts off. Selected experiments are recorded as requirements; enable those switches in Minecraft world settings too. Creating from an existing workspace opens the new project in another VS Code window, preserving the current workspace.

## Profiles and versions

Beta and stable use separate UUIDs saved in project settings. Stable retains existing pack identities when initializing an add-on. Modules receive persistent profile identities, and dependencies between the two packs are rewritten consistently.

Both profiles use one explicit three-part project version. **Bump version** updates the project config, both source manifests, every manifest module, and dependency versions linking BP/RP. Comments and unrelated manifest fields are preserved. Version updates snapshot original files and restore them if a write fails; failed recovery retains originals with a journal.

Saving never increments the version or displays a prompt. Automatic beta deployment remains silent. After a successful stable deploy/export, beta is rebuilt at the selected version and redeployed if Auto deploy is enabled; otherwise the refreshed beta build stays local. Stable actions are recorded separately in `.bedrock/state.json`. If beta refresh or version synchronization fails after a release was written, the error identifies that partial success.

Successful extension beta builds have a separate local build counter in `.bedrock/state.json`. Release filenames include the version, and exporting refuses to overwrite an existing release file. To intentionally rebuild the same version, move or delete that local export first. Stable deployment updates owned stable folders directly, without creating an mcaddon. An imported pack with the same UUID in an unowned folder must be moved/removed before stable deployment to avoid duplicates.

Set `profiles.beta.title` and `profiles.stable.title` for branding. Development folders and pack titles use `SavageCraft v2 Beta BP` and `SavageCraft v2 Beta RP`, independent of the project version. A trailing `Beta` in the configured beta title is normalized so it is included only once. Stable exports use `SavageCraft v2 1.0.0.mcaddon`, containing `SavageCraft v2 BP` and `SavageCraft v2 RP` folders. Manifest versions still track the project version, and beta/stable UUIDs remain unchanged across updates. Names are sanitized only where Windows forbids filename characters.

Deployment migrates older owned folder names and versions while keeping UUIDs unchanged. Unowned folders are preserved. If Minecraft prevents removing an emptied old folder, its manifest is removed to avoid duplicate packs and the empty folder is cleaned up on a later deployment.

Both profiles use each source pack's `pack_icon.png`. Stable builds keep it in color, and beta builds always generate a grayscale copy while preserving transparency. Source images stay in color. There are no beta-specific icon settings. Existing projects migrate old stable icon selections into source packs, then remove the obsolete per-profile icon settings; legacy beta-only selections are discarded.

Changing module count requires deliberately updating the persisted profile module UUID arrays. Keep their order consistent with the source manifests. Do not regenerate UUIDs for ordinary updates.

## Compiler

Only the configured behavior and resource pack directories are compiled. JSON comments, byte-order marks, and trailing commas normalize to plain JSON. Scripts compile from TypeScript or JavaScript to ECMAScript modules; relative imports resolve to `.js`. Script API package imports remain external. Builds detect duplicate output names, malformed JSON, missing relative imports, invalid project settings, and missing script entry points.

This first compiler transpiles TypeScript; VS Code's TypeScript service provides type checking when your project has the relevant Script API type packages and `tsconfig.json`. Compiler plugins, bridge generator syntax, npm package bundling, and path aliases are not supported. Use standard Bedrock content and relative script imports.

Deployment uses current Windows GDK locations, with legacy UWP fallbacks. It synchronizes files only inside folders bearing this project's ownership marker, keeping pack root directories in place so Minecraft can hold them open. Unchanged files are skipped, stale files are removed, and temporary file locks are retried. Before changing either pack, deployment snapshots changed and deleted files. A failed update attempts to restore both packs; if a lock also prevents recovery, previous files and a journal are retained at the paths shown in the error. A failed compile leaves deployed content intact. Minecraft may require a world reload to observe file changes.

## JSON assistance

Bundled schemas provide project settings and format-2 manifest completion/validation. Configured BP/RP paths receive compatible official schema assistance and documentation-based component help, with foundational schemas retained for older targets. Content schemas allow unknown components and are not exhaustive Bedrock runtime validators. See **Official schemas and project intelligence** below for coverage and compatibility limits.

The selected `targetVersion` sets `min_engine_version`; it does not install Minecraft, select an older game binary, change Script API dependency versions, or enable world experiments. Project experiment flags are notes for the creator.

## Textured model previews

The 0.26.1 correction fixes Bedrock-to-renderer handedness for cube/bone pivots and rotations, east/west box UV strips, and top/bottom UV orientation. Regression tests check actual texture corners and the cow neck angle; native VS Code verification uses a copied SavageCraft cow. This supersedes the first milestone's insufficient orientation checks.

Use **Bedrock: Open Model Preview** or **Bedrock: Open Model Preview to the Side** from the Command Palette, editor title, or Explorer context menu on a saved geometry, client entity, attachable, block JSON, or texture image. Normal JSON/image editing remains available. Choose the model/owner and texture when several are declared. Missing bindings are explained; aliases are candidates, not runtime decisions.

From 0.26.3, **Open Geometry Viewer to Side · geometry.…** also appears directly above geometry declarations and references in JSON/JSONC, similar to the editor's other source hints. Click it to open the associated saved owner appearance beside the JSON, including vanilla references. Use manual inspection to isolate the referenced geometry. It keeps owner/texture choices when necessary and reuses an existing preview for the same file/geometry. Save edited bindings before previewing. These source links use VS Code CodeLens (**Editor: Code Lens** must be enabled); the title/menu actions remain available independently.

Render controllers are the normal preview source of truth. Choose an owner, then use **Controller appearance** inputs derived from reachable controller branches. Only relevant client-synced properties are exposed: koi eggs/fry hide adult pattern controls; wild coloration hides unused pattern choices; setting a pattern to zero hides its palette. Supported property-derived literal arithmetic and unique straight-line pre_animation bindings resolve texture-array indices without executing project scripts. Duplicate assets and unknown runtime expressions remain explicit. When a controller has several unresolved resource branches, choose one of its reachable geometry/texture variants; alternatives are never rendered together. These are static possibilities within declared property domains, not proof that behavior events can reach every combination in-game.

Enable **Manual geometry / texture inspection** to choose raw model and texture assets independently. Opening a texture directly starts this mode. Turning the override off restores controller authority; normal saves retain appearance inputs. Manual mode is for inspecting an asset, rather than a claim about its in-game appearance.

Automatic preview renders the resolved controllers in declaration order with separate textures and per-controller bone visibility. This supports the koi's base and two alpha-cutout pattern passes, including fully transparent no-pattern TGAs. True-color/grayscale TGA images (raw and RLE), PNG and JPEG render locally with crisp pixels. Palette-mapped/16-bit true-color/interleaved TGA and arbitrary multi-sampler material composition remain unsupported. Header scrolling preserves room for the canvas.

This first milestone renders modern `minecraft:geometry` arrays and legacy `geometry.*` cube models, parent bones, pivots, X/Y/Z rotations, inflation, box/mirrored UVs, per-face UVs with signed sizes, and declared texture dimensions. PNG/JPEG and supported TGA textures have crisp nearest-neighbor filtering and transparency. Drag to rotate, right-drag to pan, wheel to zoom, and use **Reset camera**. Saved source-pack changes refresh previews while retaining available choices and camera position.

Discovery reuses Workbench's saved project resource index. Client entities/attachables provide aliases; custom blocks provide geometry and terrain-atlas material textures, including separate base/permutation and atlas-variation choices. Block previews apply one selected texture to every face. Unbound geometry can be viewed without a texture. Built-in block geometry, unrelated third-party packs, full subpack geometry/texture override selection and runtime render-controller decisions remain unresolved. Controller lookup reuses the existing resource-subpack binding context.

Vanilla geometry such as cod and salmon is supported from 0.26.2. Project models/textures override vanilla assets. Missing geometry falls back to an explicitly selected compatible vanilla pack, then to compatible released Mojang samples. The preview labels the source and version; duplicate source candidates remain selectable. Texture overrides can also resolve vanilla owners without copying a client entity into the project. Old reference caches upgrade on demand to include geometry, owners and required render-controller payloads. Project controllers override selected vanilla packs and compatible pinned sample controllers. Missing vanilla PNGs are downloaded only after selection, from the geometry reference's pinned sample tag, and cached under `.bedrock/reference/preview-assets` for offline use. Unknown custom texture paths are never guessed on the samples server. If an asset is unavailable offline, the panel explains it and keeps supported geometry viewable with a neutral texture. **Select Vanilla Reference Source** can opt into installed-pack assets; the extension never scans an unselected game folder.

Limitations: static cubes only; no animation, general runtime Molang or arbitrary visibility evaluation, polygon/texture meshes, per-face UV rotation, full material routing, block transformations or item display transforms. Materials are unlit and double-sided; alpha below 0.1 is discarded, and intersecting translucent surfaces may sort imperfectly. TGA decoding is limited to the documented raw/RLE true-color and grayscale forms. Unsaved edits are not rendered. Assets are limited to 16 MiB and models to 20,000 cubes. Previews require workspace trust. The renderer runs locally without network or project scripts; the extension host may fetch pinned Mojang references/assets. Only selected, containment-checked project or approved vanilla asset bytes reach the webview.

Native VS Code 1.143.1 verification on October 26, 2026 covered a UV/alpha fixture and a copied SavageCraft platypus with a 160×160 skin mapped to 80×80 UV space. Visual checks covered face colors, crisp edges, alpha cutouts, texture selection, orbit and zoom. A read-only SavageCraft audit converted 97 geometries across 49 files into 4,296 cube faces and discovered 139 owner bindings. This verifies preview behavior; Minecraft in-game rendering has **not** been verified. See [verification evidence and remaining milestones](PREVIEW_VERIFICATION.md).

## Development

Run `npm install`, `npm run check`, and `npm test`. Packaging uses `npm run package` with Node 22 or newer. Press F5 using the supplied launch configuration to open the SavageCraft working copy in an Extension Development Host.

After editing preview sources, run `node tools/build-preview.cjs` to regenerate the dependency-free browser asset. `node tools/prepare-preview-test.cjs` creates an isolated fixture for `test/preview-host.cjs`; `node tools/audit-preview.cjs` audits SavageCraft read-only and writes evidence under `.test-temp`.

The extension's `PROJECT_TRACKER.md` is available through **Bedrock: Open Extension Project Tracker**. The independent test add-on under `projects/SavageCraft v2` is excluded from source control and the VSIX. Its original bridge project remains unchanged.

## Target engine checks and Mojang reference data

Opening a project checks the current released Windows Bedrock engine using official Minecraft download metadata. A newer release prompts **Update target** or **Not now**. Accepting updates `targetVersion` and both source manifests' `min_engine_version` in one transaction; pack/module versions, UUIDs, content format versions, and Script API dependencies remain unchanged. The prompt does not block builds. Offline checks are quiet, never downgrade a newer target, and can be retried using **Settings > Target engine version**.

On first opening, the extension downloads Mojang's text-only [bedrock-samples release archive](https://github.com/Mojang/bedrock-samples/releases), then caches an index in `.bedrock/reference`. The HTML documentation under `documentation` is represented by `metadata/doc_modules`; item definitions also use `metadata/json_schemas`. The newest released samples at or below the project's target supply component/field completions, documentation hovers, conservative type validation, and explicit component spelling Quick Fixes for configured behavior-pack block, item, and entity folders. Component groups and block permutations are supported. Custom components and undocumented fields remain allowed. Source content is never automatically corrected on save.

Generated file-based schemas are associated through workspace `json.schemas` settings, preserving unrelated associations. Cached references work offline; **Settings > Refresh Mojang reference** forces a download retry. Samples can lag Minecraft hotfixes, so reference version and current game release are checked separately. Preview projects initially use released sample references too; Preview-specific documentation, exhaustive validation, and vanilla identifier suggestions remain future work. Downloaded documentation is used as data only and remains subject to [Mojang's repository license](https://github.com/Mojang/bedrock-samples/blob/main/LICENSE.md).

## Script dependencies and world experiments

**Settings > Beta Script APIs** selects regular APIs (Off) or beta APIs (On). The **Beta APIs** row in **World experiments** controls the same project setting, `experimentalGameplay.betaApis`. Existing bridge-era experiment names are normalized when loaded and saved under their current setting names when settings are edited. This choice is independent of beta/stable build branding and UUIDs.

The **Script dependencies** section lists modules declared by BP/RP manifests, with **Check script versions**, **Add script dependency**, and **Install matching typings** tasks. Opening a project or changing its channel/engine/API-track settings checks official Minecraft npm metadata. A prompt lists proposed manifest and exact npm type versions before applying changes. Accepting updates module-name dependencies transactionally, then installs matching typings into the project using npm; pack versions and UUIDs stay unchanged. Existing npm type dependencies are checked too. No source scripts are migrated automatically, so API changes may require code changes. Declining leaves dependencies untouched; automatic checks remain quiet offline.

Release targets use published regular APIs or Release-specific beta variants. Preview targets can use Preview RC typings for regular APIs or Preview beta typings when beta APIs are enabled. Runtime manifests receive the short API version, while npm receives the exact game-specific package version. Engine-tagged metadata bounds selections to the target engine; published stable APIs with no historical mapping rely on npm's published version information. Internal packages are excluded. Modules without beta variants retain regular typings.

Typings installation requires Node.js/npm on PATH. It uses an explicit project prefix, exact versions, disabled lifecycle scripts, and explicit shared Minecraft type dependencies so Preview peer ranges cannot substitute regular APIs. It creates or updates the project's `package.json`, `package-lock.json`, and `node_modules`. If npm fails after manifest synchronization, the error identifies that partial success; **Install matching typings** retries installation.

**World experiments** contains individual project requirement toggles filtered by target engine and Release/Preview, plus retained saved requirements for older/custom experiments. The catalog is maintained with the extension; future Minecraft builds may add or retire switches. These settings describe the world's required configuration. They do not edit `level.dat` or enable switches inside Minecraft automatically. Enable the corresponding switches in Minecraft's world settings. Beta API requirements also control dependency selection; other toggles record requirements. See [Microsoft's experiment documentation](https://learn.microsoft.com/en-us/minecraft/creator/documents/experimentalfeaturestoggle) and [Script API versioning](https://learn.microsoft.com/en-us/minecraft/creator/documents/scripting/versioning).

## Experiment reference updates

Experiment availability now uses the Bedrock sections and version history of the [Minecraft Wiki Experiments page](https://minecraft.wiki/w/Experiments#Bedrock_Edition_2), fetched as revision-stamped wikitext through its public API. Only Bedrock entries are used. Release and Preview version history, preview-only flags, and upcoming/until annotations determine availability; removed entries do not remain active merely because old translation strings still exist. Historical targets can retain experiments removed from newer Minecraft releases. The bundled catalog remains a fallback when no verified cache is available.

Checks run on project opening and target/channel changes. While VS Code stays open, the extension checks every six hours, fetching a fresh reference at most once per 24 hours. **World experiments > Check experiments** forces an online refresh. The revision and last good catalog are cached in `.bedrock/experiments`; offline errors or an unrecognized page layout retain the last good reference rather than deleting saved settings.

A popup offers **Choose experiments**, **Keep disabled**, or **Later** for active experiment requirements not previously configured/reviewed. The chooser is a multi-select list with nothing selected initially; only selected entries are enabled. Keep disabled remembers the decision without adding requirements. Later or dismissing snoozes the prompt for 24 hours; a manual check can ask again. Decisions persist per project, so ordinary sidebar refreshes do not repeatedly prompt.

Experiment rows use native VS Code checkboxes. Checking or unchecking explicitly saves the requested state, refreshes the sidebar, and keeps Beta APIs synchronized with the Settings toggle. Confirmed removed entries have no active checkbox and offer a separate prompt to remove their saved project requirements. Keeping a retired requirement preserves it with a Removed label. Deprecated entries are labeled, and unknown/custom saved settings are preserved as unverified. World files are never edited by these controls.

The reference is a community-maintained source and can change its markup; parser consistency checks protect the cached catalog. Source text is cached locally with revision attribution and is not bundled into the extension. Availability cannot be inferred safely from language-file names alone. The current 26.52 Release and 26.70 Preview lists were checked against the supplied wiki page and official Minecraft lifecycle notes during this update.

## Official schemas and project intelligence

Bedrock Workbench bundles Mojang's `@minecraft/bedrock-schemas` **1.26.50** for offline BP/RP schema assistance. It attaches only when the project target is at least that engine version; older targets keep the existing foundational/documentation schemas. Preview currently uses this compatible released schema snapshot, supplemented by the project's cached Mojang documentation. Schema package updates ship with extension updates; this feature does not automatically follow the npm beta tag.

Coverage includes entities, blocks, items, biomes, features/rules, recipes, loot tables, trading, dialogue, animations/controllers, models, particles, attachables, fogs, render controllers, texture metadata, languages, sounds, UI, and supported lighting/water/PBR documents. Associations respect the configured BP/RP paths and specific file roles. Official data is copied into `.bedrock/reference/official-1.26.50`, preserving unrelated workspace JSON associations.

The published generator has incomplete nested constraints, incorrect array/vector/root shapes in several formats, and an omitted shared expression definition. A local compatibility layer keeps document structure/type checks and completion/hover documentation while treating unreliable nested constraints conservatively. Recipe variants, texture atlases/sets, flipbook arrays, languages, trade tables, feature-rule wrappers, and schema reference bases receive targeted adapters. Unknown/custom properties remain allowed. This is not an exhaustive Bedrock runtime validator.

**Project tools > Validate project** checks saved pack JSON, manifest structure, duplicate manifest UUIDs and content identifiers, script entry paths, linked pack versions, available structural schemas, Molang syntax and documented restrictions, and project references. Results appear in Problems and `.bedrock/validation-report.json`. It does not deploy, change versions, or rewrite source files. Explicit validation scans all saved pack files; ordinary builds still use the existing compiler checks. JSON files larger than 2 MiB are omitted from the content index/explicit JSON validation; normal compiler validation is unchanged.

JSON value completions, hovers, and Go to Definition now use project identifiers and resources: item/block/entity IDs in supported fields, geometry, animation/controllers, textures/atlas names, and loot-table paths. Missing references are informational because Minecraft or another pack may provide them. The initial index is cached in memory; saved file changes update it incrementally. Global identifier suggestions from vanilla metadata and subpack-aware resolution remain future work.

Molang authoring uses Workbench's own lexer, parser, field detection and editor providers. Its independently assembled catalog covers the 378 entries in the official Microsoft Learn query/math tables, including legacy/internal entries for existing-content hovers. Expression fields in BP/RP JSON, animations, controllers, client entities, attachables, particles, geometry bindings and sound variants support contextual completion, function snippets, parameter guidance and Learn-linked hovers. Empty fields and incomplete expressions work too. Project variables and resource aliases follow unique entity ownership; temporary values stay within their expression and brace scope. Whole-string aliases and entity-property references retain their existing authoring providers to avoid duplicate suggestions.

Molang references also follow bound controllers/helpers and unsaved JSON edits. Go to Definition opens variable assignments, controller/curve declarations and resource bindings inside compound expressions. Runtime actor arrows keep private bindings separate. Function guidance includes reviewed optional-hand, equipment-index and cooldown overloads; documented version notes stay advisory when historical support is uncertain.

Use **Settings > Authoring resource subpack** to preview Molang references from a declared resource subpack. Matching subpack files replace base files; unmatched files fall back to the base pack. Editing a file inside a subpack uses that file's own subpack context. This setting changes editor references, not Minecraft's subpack choice or builds.

Validation checks syntax and explicit documented restrictions while preserving unknown runtime names and older syntax. JSON escapes map back to precise source ranges, and live findings are not duplicated by project validation. Pack `min_engine_version` controls documented Molang rule changes; document `format_version` controls the documented 1.26.0 support for brace scopes spanning client script strings. Release/Preview Learn tables currently have the same function inventory. Unknown introduction versions, dynamic types and runtime initialization remain permissive. Individual strings over 64 KiB are omitted. Exact audited coverage, sources, regeneration commands and remaining gaps are recorded in `schemas/AUTHORING.md`.

Block geometry fields suggest pack models and compatible vanilla geometries. Material-instance textures, destruction particles, item icons, blocks.json textures, and flipbook atlas tiles suggest names from the appropriate project and compatible vanilla atlas. Image-path fields suggest image paths separately. Go to Definition opens the exact project atlas entry or geometry identifier.

The Bedrock workspace disables VS Code word-based suggestions for JSON/JSONC, so unrelated words from other files do not fill empty custom component objects. Schema and project-aware completions remain enabled; custom objects without known parameters offer no parameter suggestions.

Component and nested-field documentation links use [Microsoft Learn](https://learn.microsoft.com/en-us/minecraft/creator/?view=minecraft-bedrock-stable), a primary source for requirements alongside compatible Mojang samples. The bundled URL catalog covers current and legacy component pages; custom components link to Microsoft's scripting guide. Maintainers can refresh URL metadata with `npm run docs:links`.

Item authoring now has independently maintained schemas for 52 built-in/legacy components, nested Learn-linked hovers, value choices, and array-entry starters. Block placers, digging selectors, repair ingredients, food conversions, ammunition, storage restrictions, projectile entities, icons, and supported sound fields use the appropriate project/vanilla reference lists. Existing project item tags are suggested without restricting new tags. Script-registered custom item IDs, legacy component arrays, nested parameter hints, example values, hovers, and source navigation use the same saved-source analysis as blocks, with item/block registries kept separate. Unknown custom payloads remain valid. Format/prerequisite notes do not replace an in-game compatibility check.

Vanilla reference validation uses a compatible released Mojang samples catalog by default. Known project and vanilla names resolve together; unknown names, including `minecraft:` spellings, are informational because another pack or incomplete reference data may supply them. Missing catalogs do not establish that a vanilla name is invalid. The validation report lists its samples/installed sources.

For an unresolved reference that is intentional, use its **Mark as intended** Quick Fix and select this-file or whole-project scope. Rules are stored under `validation.ignoredReferences` in `bedrock-project.json`; add an optional `reason` there. **Review intended references** in Project tools opens those settings so rules can be removed. Live checks and Validate Pack honor the same rules; ignored findings remain listed under `suppressedIssues` in the saved report. Only exact unresolved references are suppressed, never schema or syntax errors. Legacy names and asset references used by vanilla samples are recognized without duplicating completion spellings.

Optionally choose **Vanilla reference source** in sidebar settings or run **Bedrock: Select Vanilla Reference Source**. Select a readable Minecraft `Content/data` folder, a vanilla pack folder, or a samples folder, then enter its actual version. Selecting the folder grants read-only indexing; no game folder is scanned before that choice. Selections persist on this machine separately for Release and Preview, and can be disconnected with **Mojang samples only**. Expected pack layouts are inspected without following directory links; only names/paths and JSON metadata are cached. Local versions newer than the project target are excluded. Local indexes refresh after a day, or immediately when reselected. Reselect and update the declared version after updating Minecraft. Preview uses compatible released samples as a fallback; local Preview packs can supplement those names. This does not prove that a pack will load successfully in Minecraft.

Format-aware authoring uses each file's `format_version` alongside the project target engine. Component and field suggestions follow explicit Microsoft Learn requirements; incompatible usage appears in Problems and Validate Pack. Older formats are preserved. This currently covers documented BP block/item/entity requirements, including permutations, entity component groups and custom component syntax. Historical and experimental rules not documented by the sources remain permissive.

Component compatibility checks also cover audited changes in field types, renamed/removed fields, required companion components and experiment requirements. Problems offers explicit Quick Fixes for supported conversions and renames, project experiment requirements, and file format updates within the target engine. Experiment requirements must also be enabled in the Minecraft world. Fixes preserve conflicting values for manual review and never run automatically.

Entity authoring includes curated components and AI goals, event/group/property suggestions, linked controller navigation and scoped F2 rename. Known language keys and pack entity/item/block identifiers show their supplied English-first translation beside the value in green italic text. The color follows the theme and can be customized with `workbench.colorCustomizations` → `bedrock.translationPreview`; hovering the preview shows the other supplied languages. Translation-capable fields (including manifest titles, UI labels and death-message overrides) offer both vanilla and project keys with their translated text, including static script RawMessage `translate` values. Renames update known references and supplied locales together, and refuse ambiguous shared-controller changes. Dynamic script/timeline references and existing Minecraft world saves remain outside source rename coverage.

Language files use the Minecraft Language syntax mode. Keys are colored by category: entity, spawn egg, item, block, interface, action, pack metadata and other translations. Customize these theme colors through `workbench.colorCustomizations` using `bedrock.lang.entity`, `bedrock.lang.spawnEgg`, `bedrock.lang.item`, `bedrock.lang.block`, `bedrock.lang.ui`, `bedrock.lang.action`, `bedrock.lang.pack` and `bedrock.lang.other`. Key hovers list clickable pack files and line numbers using the translation, including implicit name bindings, static JSON/script references and tellraw/titleraw function messages. Unsaved JSON, script and function edits are included. A key with no indexed reference may still be used dynamically by Minecraft or scripts.

### Client entity resources

Resource-pack client entities now use an independently authored schema with Learn-linked hovers for description fields, Molang scripts, spawn eggs and legacy layouts. The same route supports older project targets. Field coverage is checked against a pinned inventory of Microsoft Learn tables and against vanilla/project sample payloads; this catches missing fields as well as missing descriptions.

Client bindings offer project and known vanilla geometry, materials, textures, animations/controllers, particles, sounds and spawn-egg atlas entries. Go to Definition opens the actual asset declaration, and matching BP/RP entity identifiers link in both directions. Animation suggestions distinguish behavior and resource packs. Linked controllers and animation effect timelines resolve particle/sound aliases from their client definitions, including legacy controller lists. Shared or runtime-dependent ownership remains advisory, and external assets can still be marked as intended. Render-controller expressions use the shared Molang authoring layer.
